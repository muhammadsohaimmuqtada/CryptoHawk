# CryptoHawk Commercial Pilot Runbook

This runbook turns CryptoHawk's repository-level readiness into a controlled real-world validation exercise. A pilot is evidence gathering, not a production certification. CryptoHawk remains a commercial-pilot candidate until the serious-impact gate in `docs/MARKET_READINESS.md` is demonstrated with representative assets.

## Pilot ownership

Assign one CryptoHawk operator and one customer security owner. Record the pilot workspace, deployment version/commit, start date, target end date, approved asset scope, data-retention policy, and escalation contact before scanning begins.

Do not onboard assets outside the approved customer scope. Private/internal targets require the deployment controls documented in `docs/PRODUCTION_DEPLOYMENT.md`; public SaaS operation keeps private-address egress disabled.

## Minimum representative estate

A serious pilot should cover more than one executable asset class. Prefer a mix of:

- TLS endpoints and X.509 certificate estates;
- SSH endpoints;
- source repositories using the repository-native collector;
- OCI/Docker image archives through the configured read-only ingress path.

Record why each asset is representative of the customer's real cryptographic estate. Do not use synthetic-only assets as the basis for a GA claim.

## Baseline

1. Deploy from a pinned, verified CryptoHawk commit or release candidate.
2. Apply database migrations and verify API readiness.
3. Configure the customer workspace and least-privilege memberships.
4. Configure the effective cryptographic policy baseline.
5. Configure retention and deletion policy.
6. Configure enterprise OIDC when required and validate it against the customer's real IdP.
7. Register representative assets and run the initial discovery scans.
8. Export the first pilot evidence bundle.

The evidence bundle endpoint is:

`GET /api/v1/workspaces/{workspace_id}/reports/pilot-evidence.zip`

A Viewer or higher workspace role may export it. The ZIP contains:

- `manifest.json` with SHA-256 digests and policy/workspace provenance;
- `executive.json` and `executive.csv`;
- `engineering.json` and `engineering.csv`;
- `executive.html`;
- `cbom.cdx.json` using CycloneDX CBOM output.

The manifest verifies bundle integrity. It deliberately states that the bundle itself does not certify pilot success.

## Continuous-operation phase

Run the environment long enough to exercise scheduled scans, queue leases/retries, repeated evidence reconciliation, and cryptographic drift. The exact duration depends on customer scan cadence, but the pilot must include multiple successful scheduled occurrences for the representative assets rather than a single demonstration scan.

During the pilot, record:

- scheduled scans completed and failed;
- operator intervention required;
- queue or database recovery incidents;
- new, changed, and resolved cryptographic observations;
- remediation items created, owned, due, verified, or accepted as risk;
- policy changes and exact policy-version/rules-hash provenance;
- data-loss, duplicate-evidence, or tenant-isolation incidents.

Do not hide failed scans. A failure that is correctly diagnosed, retried, and recovered is useful pilot evidence.

## Migration proof

Select at least one meaningful cryptographic exposure and take it through the evidence-backed remediation workflow:

1. create remediation work from retained finding evidence;
2. assign owner, priority, due date, and migration target;
3. implement the change outside CryptoHawk;
4. run a newer successful scan of the same asset;
5. let CryptoHawk verify that the original stable fingerprint is absent;
6. retain the verification evidence.

`verified` must remain evidence-only. Do not manually mark work verified to satisfy a pilot criterion.

## Tenant and authorization proof

Where the pilot uses more than one workspace, validate that a user or API key from one workspace cannot read reports, evidence, remediation, credentials, jobs, or assets from another workspace. Use non-production test principals for negative authorization checks.

Do not attempt destructive cross-tenant testing against customer data without explicit authorization.

## Evidence checkpoints

Export a pilot evidence bundle at minimum:

- after the baseline scans;
- after a meaningful drift event or policy/remediation change;
- at pilot closeout.

Store each ZIP in the customer's approved evidence repository. Preserve the ZIP bytes unchanged so the SHA-256 values in `manifest.json` remain verifiable.

For each checkpoint, record the deployed Git commit/release identity separately from the workspace bundle. Release/build provenance generated by GitHub Actions proves what repository artifact was built; the workspace bundle proves what CryptoHawk observed in the pilot environment.

## Serious-impact pass criteria

A pilot may satisfy CryptoHawk's serious-impact gate only when evidence demonstrates all of the following:

1. cryptography was discovered across multiple representative asset classes;
2. asset identity and evidence were preserved across repeated scans;
3. organization/workspace authorization boundaries held;
4. migration priorities incorporated business context such as exposure, criticality, and data lifetime;
5. portable CBOM and remediation evidence were exported and independently consumable;
6. meaningful cryptographic drift was detected between scans;
7. the platform operated continuously for the agreed pilot interval without data loss and without unacceptable operator intervention.

A failed criterion is a pilot finding, not something to waive silently. Record the gap, severity, owner, corrective action, and retest evidence.

## Additional GA gates outside the product code

The repository cannot complete these on its own:

- representative customer/design-partner pilot evidence;
- independent security assessment or penetration test and closure of material findings;
- deployment-specific HA/failover validation where HA is sold or contractually promised;
- customer-specific privacy, retention, deletion, support, incident-response, and SLA approval;
- real IdP validation when enterprise SSO is used.

These require an external environment, customer stakeholders, or an independent assessor.

## Closeout decision

At closeout, classify the pilot as one of:

- **PASS** — all serious-impact criteria demonstrated and no unresolved material blocker;
- **PASS WITH ACTIONS** — value demonstrated, but explicit non-material actions remain before broader rollout;
- **FAIL / EXTEND** — one or more serious-impact criteria lack evidence or a material reliability/security issue remains.

Attach the baseline, intermediate, and closeout evidence bundles to the decision record. Do not change CryptoHawk's public positioning from commercial-pilot candidate to generally available production software based only on repository CI or a synthetic demonstration.
